# How good is the new atlas map? A plain-language benchmark report

*Tests run on 12 September 2026. Rerun after the off-map cutoff was calibrated the same day. Every number here comes from the files in `results/`; the technical version of this report is [REPORT-technical.md](REPORT-technical.md).*

## The short version

The atlas is a fixed map of text. The new version, **atlas-v3**, has 4,096 small areas grouped into 256 larger areas, and every area has a hand-written name. When you hand the tool a dataset, it places each record on the map and tells you which areas your data fills, which it barely touches, and which it never reaches. We tested whether the new map does that job well, using data it had never seen during its construction, and we compared it with the map it replaces.

**Verdict: the new map is clearly better than the old one at every task we could measure, and its names are trustworthy.** It sorts unfamiliar data into the right areas, it sees the subject of a text rather than the language it is written in, and it can spot a small slice of unusual data hidden inside a large corpus. Two things around the map needed fixing. One, the rule that decides when a record is "off the map", has been fixed since the first run. The other, a comparison feature that over-reports how much of a small dataset is new, is being worked on.

## The atlas in one minute

- Think of a **city map** with 256 districts, each split into a handful of neighbourhoods, 4,096 in all. A district might be *Recipes, cooking and home kitchens*; one of its neighbourhoods might be *Pizza recipe and restaurant articles*.
- The map was drawn once from a very large public collection of text, 163 million documents in about 60 languages, and it never changes. That is the whole point: two datasets placed on the same map can be compared, the way two shops can be compared by their addresses.
- To place a record, the tool turns its text into a list of numbers that captures what it is about, then finds the neighbourhood whose typical text is most similar. The record also gets a **similarity score** between 0 and 1: how much it resembles that neighbourhood's typical text.
- If the score is below a **cutoff**, the record is **off the map**: it resembles nothing the map knows. That cutoff is now 0.354, set by the calibration described below.
- The tool then reports **coverage**: how much of your data sits in each district, and how that compares with the map's own mix. A district where you have three times the map's share is a **3× density**.

## How we tested

### The rules we followed

1. **Test on data the map has never seen.** A map built from a pile of text will naturally place that same text well, the way a student does well on questions copied from the textbook. So the test data came from 52 public datasets that were *not* used to build the new map, plus four well-known exam and translation benchmarks that no version of the map was built from. Where we did use data of the same kind the map was built from, the report says so, and it is never used for the sorting scores.
2. **Every map gets exactly the same records**, and every record goes through exactly the same steps a real user's run goes through: the same text window, the same encoder, the same language detection, the same placement rule, the same cutoff. Nothing was tuned for the test.
3. **Always show what luck would get.** A score means nothing without knowing what guessing would score. Every sorting result is shown next to the score you would get by always guessing the most common answer.
4. **Always show the best possible score.** For each sorting test we also trained a proper classifier on the same information the map uses. Its score is the ceiling: how much the underlying text understanding knows. The map's score against that ceiling tells you how much the fixed grid keeps.
5. **Never let a map grade its own homework.** Sorting scores are computed on records the scoring rule never saw (see the next section). Names were judged blind, with the map's identity hidden and the items shuffled.
6. **Compare like with like.** The new map has 4,096 areas; the old one has 296. Some statistics reward having more areas no matter what. Those statistics are shown only in the technical appendix and only compared between maps with the same number of areas. The plain scores above are fair across maps.
7. **Save everything.** Every placement, every number and every terminal printout is in `results/` and `runs/`, and the whole suite reruns from one command listed in the README.

### How a sorting score is computed

Take 52,000 records, 1,000 from each of 52 datasets. Place them all. Split them in half at random.
- On the first half, look at each neighbourhood and note which dataset most of its records came from. That becomes the neighbourhood's label. This is a **majority vote**.
- On the second half, for each record, guess the label of the neighbourhood it landed in. Count how often the guess is right.
- That count is the score. It is deliberately the weakest possible way to read the map: no training, no clever model, just "records that land here usually come from X". If that alone works, the map is carrying real information about the data.
- **Luck** is the score you get by always guessing the single most common dataset. **Ceiling** is what a trained classifier scores on the same second half using the same numbers the map uses.

### Steps, in order

1. Load the four maps and the encoder. Confirm the encoder is the one each map was built with.
2. Read the test datasets. Drop records shorter than 80 characters, because the tool itself does not place those.
3. Detect each record's language, the way the tool does, because the new map adjusts for language before placing.
4. Place every record on every map. Keep the neighbourhood, the district, the similarity score and the top-5 nearest neighbourhoods.
5. Score sorting (datasets, kinds, subjects) with the majority-vote rule, next to luck and the ceiling.
6. Score the language tests: do translations and same-topic texts land together, and how much does an area's identity reveal about language.
7. Score coverage: hide a slice of one dataset in the web corpus at six sizes and check whether the tool sees it and measures it; build a corpus in nine steps of increasing breadth and check the breadth reading rises; run the tool's own comparison on ten pairs of datasets; split datasets in half and check the two halves read as the same dataset.
8. Score the names: embed each name with the same encoder and check it points at its own area; place the map's own example texts back and check they return home; have a blind judge rate the names against the data that lands there.
9. Time a full-size run and run the real command on three small corpora, keeping the printouts.
10. After the first run, the off-map cutoff was calibrated by a separate piece of work. We re-applied the new cutoff to every stored placement, confirmed the map's areas had not moved, and regenerated every number.

## Results in detail

### 1. Keeping datasets apart

| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| new map (v3) | 0.7% | 31 in 100 | 51 in 100 | 65 in 100 | 66 in 100 | 82 in 100 |
| previous v3 build | 1.1% | 30 in 100 | 50 in 100 | 65 in 100 | 66 in 100 | 82 in 100 |
| old map (v2) | 11.8% | 24 in 100 | 35 in 100 | 66 in 100 | 62 in 100 | 82 in 100 |
| old small map (v2-lite) | 16.9% | 17 in 100 | 24 in 100 | 57 in 100 | 55 in 100 | 77 in 100 |

**How to read this.** From nothing but where a record landed, the new map names its source dataset right 31 in 100, where luck gives 2 and a trained classifier gives 65 in 100. So the fixed grid keeps about half of what could be known. If we allow the five nearest neighbourhoods instead of one, it rises to 51 in 100. Sorting by *kind* of data (code, math, law, science, chat, question answering, SQL, web) is right 66 in 100. The old map dropped 12% of these ordinary records off the map; the new one drops 0.7%.

### 3. Subject, not language

| map | same topic, different language: same district | different topic, same language: same district (lower is better) | a sentence and its translation share a district | by luck | translation is among the 5 nearest areas | off the map, English / Turkish |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| new map (v3) | 49% | 0% | 40% | 2% | 62% | 1.9% / 6.4% |
| previous v3 build | 29% | 22% | 40% | 3% | 59% | 4.1% / 11.1% |
| old map (v2) | 30% | 22% | 41% | 4% | 61% | 28.6% / 39.2% |
| old small map (v2-lite) | 39% | 25% | 38% | 7% | 57% | 40.2% / 43.5% |
| new map, language correction off | 42% | 1% | 39% | 2% | 57% | 3.9% / 6.3% |

**How to read this.** We wrote 14 topics, such as photosynthesis and monetary policy, in four languages. On the new map the same topic lands in the same district 49% of the time across languages, up from 29% on the previous build, and two different topics in the same language were put together 0% of the time, down from 22%. That last number is the one that matters most: the previous build had areas that meant "Turkish text" rather than a subject, and this one does not. On 8,000 real news sentences and their Turkish translations, 40% of pairs share a district where luck would give 2%. That figure is almost the same on every map, so it is a property of the text encoder underneath rather than of the map. Turning the new map's language correction off costs 7 points on the topic test, so that correction is doing real work.

A second view: place web pages in nine languages and ask how much an area's identity gives away about language. If areas were pure subject, knowing the area would say nothing about language.

| --- | ---: | ---: | ---: |

| previous v3 build | 24% | 3.6 | 0.5% |
| new map, language correction off | 21% | 3.8 | 0.6% |

On the new map 12% of web records sit in single-language areas, down from 24% on the previous build; switching the language correction off puts it back to 21%. Every language placed at 99% or better; on the old map, 13% of Chinese pages and 10% of Turkish pages fell off the map.

### 4. Finding a small slice hidden in a big corpus

We took 40,000 English web pages and hid a slice of a different dataset inside, at sizes from a quarter of a percent (100 records) to 10% (4,444 records). Then we asked: does the tool see the slice, and does it measure its size correctly? "Seen" means the extra records in the slice's home areas could not be explained by chance, and the estimated size is within a factor of two of the truth.

| hidden slice | new map: smallest slice seen | previous v3 build | old map | old small map |
| --- | ---: | ---: | ---: | ---: |
| EU regulations (eurlex) | 0.25% | 0.25% | 0.50% | never |
| Python commits | 0.25% | 0.25% | 0.25% | 1.00% |
| Math word problems (orca-math) | 1.00% | 1.00% | 2.00% | 5.00% |
| Turkish instructions (InstrucTurca) | 2.00% | 2.00% | 5.00% | 10.00% |
| Text-to-SQL (gretel) | 1.00% | 1.00% | 2.00% | 2.00% |
| Biomedical QA (PubMedQA) | 0.25% | 0.25% | 0.50% | 0.50% |
| Turkish web (fineweb-2 tr) | 2.00% | 2.00% | 5.00% | never |

**How to read this.** A slice with a distinctive home, such as EU regulations, is seen at 0.25% and its size is measured almost exactly: 0.25% estimated for a true 0.25%, and 10.06% for a true 10%. Slices that are themselves mixtures, such as Turkish instruction data, share their home areas with ordinary web pages, so they need to be about 2% before they stand out, and their size is under-read by about a quarter (7.0% for a true 10%). What the tool actually prints follows the same pattern: the main EU-law neighbourhood reads 0.3× the map's density with no slice and 72× with a 10% slice.

**How to read this.** "Share of the map covered" counts an area as fully covered when your data is at least as dense there as the map's own data, and as a fraction when it is thinner. A large sample of ordinary English web pages tops out at 64% of the map from about 20,000 records onward: the remaining third of the map is made of things English web is not, such as code, law, other languages and training prompts. That is the intended reading.

### 6. Comparing two datasets

The tool can compare two placed datasets and report how similar they are and how much of one sits in areas the other never reaches ("new"). We ran it on ten pairs.

| pair (5,000 records each) | new map: similarity (1 = identical) | new map: share of the left dataset that is "new" | old map: similarity | old map: "new" |
| --- | ---: | ---: | ---: | ---: |
| same corpus, two halves | 0.93 | 19% | 0.99 | 0% |
| alpaca vs its Turkish translation | 0.66 | 20% | 0.76 | 1% |
| Turkish instructions vs English instructions | 0.36 | 47% | 0.46 | 2% |
| hendrycks algebra vs intermediate algebra | 0.94 | 9% | 0.91 | 5% |
| Python commits vs Python text-to-code | 0.18 | 69% | 0.08 | 18% |
| eurlex vs ECtHR case law | 0.00 | 98% | 0.03 | 52% |
| Turkish web vs English web | 0.18 | 47% | 0.46 | 4% |
| Turkish wikipedia vs English wikipedia | 0.21 | 26% | 0.49 | 1% |
| Python commits vs ultrachat | 0.07 | 48% | 0.08 | 3% |
| PubMedQA vs eurlex | 0.00 | 94% | 0.01 | 6% |

**How to read this.** The big picture is right on both maps: unrelated datasets read as 0 similar; two flavours of competition algebra read as almost the same; an instruction set and its own Turkish translation read as mostly shared. The problem is the first row. Two halves of the *same* dataset should read as identical, and on the new map they read 19% new. The reason is the map's fineness: 5,000 records spread over 4,096 neighbourhoods leave many neighbourhoods with one or two records, and the two halves happen to hit different ones. The tool counts those gaps as novelty.

The same effect against sample size, on a chat dataset:

| records per half | new map: "new" between the two halves | new map: how alike the halves are at district level (1 = identical) | old map: "new" |
| --- | ---: | ---: | ---: |
| 250 | 69% | 0.80 | 24% |
| 500 | 65% | 0.88 | 14% |
| 1,000 | 46% | 0.95 | 7% |
| 2,000 | 35% | 0.97 | 2% |
| 5,000 | 18% | 0.99 | 0% |
| 10,000 | 8% | 0.99 | 0% |

At the district level the halves look alike from 1,000 records; at the neighbourhood level they need about 10,000. Until the comparison is changed to work at district level or to allow for this, treat the "new" percentage on the new map as an upper limit for datasets under 10,000 records. That change is in progress.

### 7. Text that does not belong, and the cutoff

A record whose similarity to its nearest neighbourhood is below the cutoff is off the map. When we first ran the tests, the new map shipped without its own cutoff and a generic default of 0.35 applied. Since then the cutoff has been set properly, to **0.354**, by the rule the documentation promises: it is the point below which only 2 in 100 records of the map's own building material fall, measured on a 1,998,898-record sample balanced across languages and kinds of text. The number barely moved, so the results below are essentially unchanged.

| what was placed on the new map | share off the map |
| --- | ---: |
| ordinary held-out text (52 datasets) | 0.7% |
| a typical English web corpus | 0.15% |
| machine junk (base64, hex, DNA, minified code, number columns, random characters) | 0% |

**How to read this.** Ordinary text is placed almost always, which is what the cutoff is for. The surprise is the junk: none of it falls off the map, on any version of the map. We checked whether a higher cutoff would help. It would not, because on this text encoder junk scores about as similar to the map as real prose does: a cutoff that rejects half the junk (49%) also throws away 9% of ordinary web pages. The cutoff cannot tell junk from prose; that job belongs to the tool's other checks, which look at the shape of the text itself, such as how much of it is whitespace and letters. Those checks exist, but today they only run on records the cutoff already removed, so they never see this junk. That is the remaining gap.

Why the calibrated cutoff is lower than an English-web reader might expect: the map's building material includes code and training prompts, which sit less snugly in their areas than prose does. Balancing the calibration across all of it gives 0.354; English web pages alone would give about 0.425. One cutoff serves every kind of text, so a corpus of nothing but code will read a few percent off the map without anything being wrong with it, and the tool's off-map description says what the records are so the reader can tell.

### 8. Are the names right?

| check | new map | previous v3 build |
| --- | ---: | ---: |
| a neighbourhood's name, embedded like a record, points at its own neighbourhood first (out of 4,096) | 31% | 25% |
| ... or within the ten nearest | 65% | 57% |
| a district's name points at its own district first (out of 256) | 73% | 62% |
| the map's own example texts, placed again, return to their own neighbourhood | 53% | 30% |
| ... or at least their own district | 72% | 43% |

**How to read this.** The first three rows ask whether a name and its area mean the same thing to the encoder. Pointing at the right one of 4,096 first is a hard target; a third of neighbourhood names do it and two thirds get within ten. District names hit first almost three times out of four. The last two rows use the four short example texts the map stores for every neighbourhood: placed again, most return to their own district. All five numbers improved over the previous build.

Finally, a blind judge. For each of the 52 datasets and 79 exam subjects we took the name of the area holding most of its records, shuffled everything, hid which map it came from, and had a language model score whether the name describes the data: clearly, partly, or not at all.

| names judged | clearly describes the data | partly or too generic | unrelated | items |
| --- | ---: | ---: | ---: | ---: |
| new map, neighbourhood names | 72% | 20% | 8% | 131 |
| new map, district names | 58% | 34% | 8% | 131 |
| old map, district names | 40% | 50% | 10% | 131 |

The cases the judge marked unrelated on the new map are mostly general chat datasets, which have no single describing area by construction, plus a code dataset stored as a stream of tokens rather than readable code. On the old map the judge also found competition math filed under banking and text-to-SQL under government regulations; the new map gets those right.

Name hygiene: no duplicate names at either level, 5,028 distinct words across the 4,096 neighbourhood names, and six names that use a nationality adjective ("Japanese baseball", "German municipalities") where the naming rules ask for the place. Those are the only slips found.

## What was fixed, and what still needs work

- **Fixed: the off-map cutoff.** The first run found the new map shipped without one. It is now calibrated at 0.354 by the documented rule, stamped into the map file with a record of how it was computed, and a test fails if a future build ships without it. Practical effect: almost none on ordinary data.
- **In progress: the comparison feature.** On the new map, "new" is over-reported for datasets under about 10,000 records because the map is so fine. The fix is to compare at district level or to allow for the expected gaps; a separate piece of work is on it.
- **Open: machine junk.** The cutoff cannot keep base64, hex dumps, DNA strings or minified code off the map, and the checks that can are only run on records the cutoff removed. They should also run on placed records, or the tool should report the share of such records separately.
- **Minor: six names** use a nationality adjective where the naming rules ask for the place name.

## Things to keep in mind

- The 52 test datasets were never used to build the new map, but some of them *were* used to build the old map. If anything, that flatters the old map.
- The web and Wikipedia pages used for the language tests come from the same public sources the new map was built from. They were never used for the sorting scores.
- "Which dataset did this come from" is a stand-in for "what is this about". Two math datasets are genuinely alike, and a map that cannot tell them apart is not worse for it. The "kind of data" scores are the fairer read.
- The name judge is one language model, one pass. Treat its table as a sanity check, not a measurement.
- Everything was run on one machine, on one day, from cached copies of public datasets. The README says how to rerun it.

## Words used in this report

- **Record**: one document, message, question or code file from a dataset.
- **Placing**: finding the neighbourhood on the map whose typical text a record most resembles.
- **Similarity score**: a number from 0 to 1 saying how much a record resembles its neighbourhood. Records below the cutoff are off the map.
- **Neighbourhood / district**: the map's 4,096 small areas and 256 large areas. The technical report calls them cells (L2) and regions (L1).
- **Density**: your share of an area divided by the map's own share of it. 1× means the same as the map; 10× means ten times denser.
- **Share of the map covered**: adds up, over all areas, how fully each one is covered, counting an area as fully covered once you match the map's density there.
- **Luck**: the score from always guessing the most common answer.
- **Ceiling**: the score a trained classifier gets on the same information, the most the map could have kept.
- **Held-out**: data that was not used to build the thing being tested.
- **Blind judge**: a rater who does not know which map produced what.
